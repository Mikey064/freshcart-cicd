Why this base image: checkout-api's final stage moved from node:20-alpine to a distroless-style minimal runtime approach was considered, but we settled on keeping node:20-alpine with an explicit npm install -g npm@latest — this patches the CVEs bundled inside npm itself (tar, sigstore, picomatch) without giving up the debuggability of having a shell available in the container. storefront's final stage uses nginx:1.29-alpine for the same reason: small, well-maintained, and only one apk upgrade --no-cache away from a clean scan.

Why this layer order: Dependency manifests (package*.json) are copied and installed before application source in both Dockerfiles. Docker's build cache is content-addressed per layer — as long as package.json/package-lock.json are unchanged, npm ci is skipped entirely on rebuild, and only the fast COPY src + compile steps re-run.

Why a volume here and not there: Only Postgres holds state that must survive a container restart or replacement. checkout-api and storefront are rebuilt from source on every image build and hold nothing that needs to persist between runs — a volume there would just be dead weight.

What the scan found and what we did about it: checkout-api's initial scan flagged 8 findings (1 critical) — all inside npm's own bundled dependencies, not our application code. Fixed by upgrading npm in the final stage before installing production deps. storefront's scan flagged 11 HIGH findings, all in the alpine base's OS packages (openssl, curl, libxml2, etc.) — fixed with a single apk upgrade --no-cache layer added to the final stage.
